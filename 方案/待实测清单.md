## 0. 使用方式

每项必须有：前置条件、步骤、通过标准、失败时的架构分支。阻塞项（T1–T4）没有结论前，不得把对应实现写成产品代码。

建议顺序：T0 → T1 → T2 → T3 → T4 → 其余。机型至少覆盖：一台常见品牌手机、一台安卓平板；若有 Pixel / 接近 AOSP 的设备，优先加测。

## T0 · 设为默认主屏幕（基线，非阻塞但必须先做）

**要回答：** 本应用声明 HOME 后，能否出现在系统的「默认桌面应用」列表里，并在用户选择后稳定响应 Home。

| | |
|---|---|
| 步骤 | 安装调试包；打开「设为默认主屏幕」；在系统选择器中选 Android Desk；按 Home、从其他应用返回、重启设备后再按 Home |
| 通过 | 以上路径都回到本桌面，且进程被杀后仍能被系统拉起为桌面 |
| 失败分支 | 若某 OEM 列表中根本不出现：记录规避（如需要「允许受限制的设置」、厂商启动器锁定），PRD 引导文案要写品牌差异；若无法成为 HOME，则产品主路径不成立，必须停下来改声明或放弃该机型承诺 |

补充：同时测试「预览模式」（不设默认）下普通启动是否可用。

## T1 · 手势导航与桌面横滑是否冲突（阻塞）

**要回答：** 在全面屏手势下，左右滑桌面分页会不会被系统当成返回或切入应用；底栏/任务栏是否被手势条挡住。

| | |
|---|---|
| 步骤 | 系统改为手势导航；在首页、非首页、打开抽屉时分别从边缘与从中部横滑、上滑 |
| 通过 | 有可教给用户的稳定分区：例如边缘留给系统，中部留给分页；或系统提供了兼容 inset |
| 失败分支 | 若无法与系统手势共存，桌面分页改为一组明确的页指示器点击 + 非边缘滑动，或提供「按钮导航优先」说明；不得在用户无法返回的情况下强制横滑 |

## T2 · 第三方启动器能否以自由窗口打开应用（阻塞）

**要回答：** 在已开启 freeform / Desktop Windowing 的设备上，本桌面能否用公开 API 把一个普通应用以自由窗口启动，并保持自身桌面在下面可见。

| | |
|---|---|
| 步骤 | 在支持的平板或已打开开发者自由窗口的设备上，从本桌面启动一个标准应用；观察 windowing mode、本桌面是否还在、能否再打开第二个窗口 |
| 通过 | 至少能启动 1 个自由窗口且桌面仍可见 |
| 失败分支 | 若只有系统启动器做得到：桌面窗口形态改为「仅在系统已处于桌面模式时适配」，或把多窗口降级为 Phase 后期 / 虚拟屏备选（T3）；MVP 只承诺启动器形态 |

此项是平板体验的分水岭，结论必须写进机型能力表。

**探针每次记录（2026-11-12 增补，依据见 [开源借鉴评估.md](./开源借鉴评估.md) §4.1、§4.5）：**

| 记录项 | 说明 |
|---|---|
| 系统版本与厂商系统版本 | 至少覆盖 Android 12、13、14、15、16 各一档。Android 12 是已知的断崖：对照项目在该版本上把这项能力判为不可用 |
| 系统特性 `FEATURE_FREEFORM_WINDOW_MANAGEMENT` | 有 / 无 |
| 全局设置 `enable_freeform_support`、`force_resizable_activities` 的值 | 只读取，探针不改写 |
| 目标屏幕是否默认自由窗口 | |
| 启动方式 | 只用公开接口（启动位置、目标屏幕）是否足够；是否必须反射设置窗口模式 |
| 启动结果 | 实际的窗口模式与位置，以系统报告为准，不以「调用没有报错」为准 |
| 桌面是否仍可见；能否再开第二个窗口 | |

**结论分两级写：** ① 能否以自由窗口**启动**；② 能否**移动、缩放**已有窗口。对照项目里第二级都要 root 或 Shizuku，预期第三方桌面做不到；若实测如此，窗口形态按「只能启动不能摆」设计。

**边界：** 探针不得要求用户用 adb 授予 `WRITE_SECURE_SETTINGS`，也不得依赖 Shizuku 或 root。需要这些才成立的结果记为「需特权」，不算通过。

## T3 · 虚拟屏合成是否可作为备选（阻塞，但是否采用另评）

**要回答：** 用 VirtualDisplay + MediaProjection（或等价方案）把应用打到虚拟屏再画回桌面，输入能否对得上，延迟是否可接受。

| | |
|---|---|
| 步骤 | 创建虚拟屏，启动目标应用，把画面合成到本桌面，转发一次点击并核对命中 |
| 通过 | 点击命中稳定、延迟达到「文字工作可用」（目标另见设计，先记录实测毫秒） |
| 失败分支 | 放弃自绘窗口，只保留系统自由窗口或全屏启动 |
| 采用门槛 | 即便通过，也只有在 T2 失败且产品明确需要「无系统自由窗口时的多窗口」时才进入方案；不自动成为主路径 |

预期（2026-11-12 增补）：对照项目的机型表显示，虚拟屏路线对厂商高度敏感，且都需要特权运行时（见 [开源借鉴评估.md](./开源借鉴评估.md) §4.7）。本项若要测，结果同样按机型和系统版本分档记录。

## T4 · 本应用无障碍对「操作本桌面 + 操作其他应用」的能力（阻塞）

**要回答：** 作为启动器的无障碍服务，能否读取当前前台应用并执行点击/输入；对本桌面内部控件，是该走无障碍还是必须走内部 API（预期是后者）。

| | |
|---|---|
| 步骤 | 开启本应用无障碍；在桌面上用内部 API 翻页（对照）；在另一个应用里执行点击与输入；试一次输入法中文输入 |
| 通过 | 其他应用可点击；中文输入路径可描述（直接写入节点 / 需用户键盘 / 失败） |
| 失败分支 | 若 OEM 限制启动器持有无障碍，引导文案要写「允许受限制的设置」；若中文输入不可靠，输入原语改为「请求用户输入」并在 SDK 里标明 |

补测两项（2026-11-12 增补，对应 [助手宿主架构.md](./助手宿主架构.md) §10.1 的 G3、G6）：

- 无障碍服务能否分辨一次点按落在**本桌面自己的窗口**上（确认卡、设置页），从而拒绝执行。
- 无障碍服务能否可靠识别应用标记的**安全窗口**。识别不了的话，G6 无法落地，要如实写明。

## T5 · 已安装应用可见性与图标（需量化）

不同 OEM 对 `QUERY_ALL_PACKAGES` 与包可见性收口不同。记录：不声明该权限时抽屉漏了哪些应用；声明后商店政策风险只作备注（MVP 侧载）。

---

## T6 · 小组件宿主（Phase 2，不阻塞 M1）

能否作为 AppWidgetHost 添加、缩放、响应一个系统时钟小组件。失败则小组件延期，不影响桌面图标。

---

## T7 · 与 DSH Go 并存（M6 前必须做）

安装 DSH Go，本桌面设为 HOME。记录：对方桌宠是否仍显示、无障碍能否同时开启两套、从本桌面启动 DSH Go 是否正常、是否出现焦点或输入法冲突。结论回填「两只桌宠」的提示文案。

另测一项（2026-11-12 增补）：DSH Go 的**插件**能否调用到本桌面的助手入口（ContentProvider 的 `call()`，见 [开发方案.md](./开发方案.md) §6）。目前未知。结论决定「协作接入」能否走对方的插件，还是必须对方改代码。

---

## T8 · 冷启动与重回桌面耗时（需量化）

记录：开机后第一次按 Home、从重型应用按 Home、进程被杀后按 Home 的时间。回填 PRD「观感应与系统启动器相当」的数字，不先写死营销值。

## T9 · 能否直接回到厂商桌面（需量化）

**要回答：** 从本桌面用显式 Intent 拉起设备上另一个 HOME 应用（系统自带桌面），各品牌是否放行。对应 [功能设计.md](./功能设计.md) F2。

| | |
|---|---|
| 步骤 | 本桌面分别处于「默认」与「预览」两种状态，点「回到系统桌面」；之后按 Home，记录去了哪里 |
| 通过 | 对方桌面被调到前台；之后按 Home 的去向与系统默认设置一致 |
| 失败分支 | 被拦截或无反应的品牌：走降级对话框，引导去系统设置更换默认桌面；机型记入能力表 |
